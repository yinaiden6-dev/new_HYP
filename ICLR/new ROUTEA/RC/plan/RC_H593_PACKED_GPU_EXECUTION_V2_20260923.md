# H593 多 GPU 统一执行池

用户授权将当前排队任务包装进一个 dev 多 GPU/CPU 作业，并行执行同一 H593 上的不同信息提取和融合训练。仅修改执行调度；既有科学源码、数据划分、FP64、完整 C128、干预定义、训练更新顺序和验证器均保持原状。

申请一个节点、4 GPU、32 CPU、256G。四个独立 Slurm job step 各占 1 GPU、8 CPU、64G；每项工作调用原冻结程序的独立新进程，避免不同实验的 hook 或全局变量互相污染。任务池涵盖 inside、visual、coordinate 三类 query 分片及 fusion 的配置训练/预测分片；每个融合配置在同一 allocation 内至多出现一次，保留原正常退出 receipt 的唯一性。真实 Job ID 和 step GPU 分配均记录，不伪造旧数组身份。

先做四项试运行：每类一项。几何分析必须通过原完整 C128 验证，融合须正常保存可续跑 checkpoint 并生成原 chunk receipt。四个 step 必须绑定不同 GPU。试运行 30 分钟，正式池每次 55 分钟；不在剩余不足 15 分钟时启动新的原程序，给原 850 秒保护退出和最终封存留余量。

先暂停本次接管范围内的待运行计算及 CPU 续提任务，运行中的任务自然完成，试运行依赖这些运行任务成功结束。既有缓存/部分结果原位续跑。试运行失败自动释放被暂停的旧任务，不直接取消旧队列。只有原验证器和四卡分配验证通过，才取消已被接管的三类图像分析待运行计算/回调；保留 M-path readout 控制任务，待 inside 全量完成后释放。

旧融合调度器位于另一个登录节点，V2 不要求跨节点控制其进程。融合数组保留为 held 状态，使原调度器不再提交重复训练波次；新池负责计算，原调度器继续观察原 200 个配置的验证文件并负责最终 join。最终融合汇总通过后才清理这些 held 占位任务。若原调度器达到自身期限、明确写出 STOPPED 状态，新池才接替提交最终 join。未提交的 V1 仅保留为工程历史，没有修改任何科学结果。

正式池每次从未完成 query 和未完成配置中公平选择最多 32 项，空闲 worker 动态领取。统一调度器在登录节点仅做轻量队列/文件状态检查；模型计算全部在 Slurm GPU allocation 中执行。它直接接续新的合并作业，不再要求每批 GPU 工作先经过单独排队的 CPU 回调。最长自动执行 72 小时、最多 128 个合并作业；失败时封存状态并停止自动扩展。

数据完整后调用原 join/后续拟合入口，保留其标签门。M-path readout 仍等全部 inside 数据齐全；不提前读取留出标签。本次不改变统计比较，也不产生新实验臂。同图可以共用已有磁盘缓存和操作系统页缓存；不同干预仍按各自原算法计算，不能把它们擅自替换成一次共同前向。

输出：`results/rc_h593_packed_gpu_v2/`。所有迁移/暂停/接管、原进程命令、Slurm spool、每项命令/日志、原验证或 checkpoint 引用、四卡映射和计时均保留。2 GPU、4 GPU 的 `sbatch --test-only` 已由调度器接受；这只证明资源请求合法，不证明已经获得资源或达到四倍加速。
